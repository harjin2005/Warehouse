# LeanBridge OI — Multi-Tenant SaaS Rebuild Design

## Context

The existing repo (github.com/harjin2005/Warehouse) is a Gemini AI Studio prototype: a
single-page React/TS app with no backend. It uploads warehouse Excel files (orders, picks,
inventory) and asks Gemini — via prompts, from the browser — to parse columns, validate data
quality, compute KPIs (cycle time, percentiles, trends), evaluate rule thresholds, and propose
corrective actions. Two disqualifying defects block any real sale:

1. **Exposed secret** — `vite.config.ts` bakes `GEMINI_API_KEY` into the client bundle. Any
   visitor can read it out of devtools.
2. **Non-deterministic business math** — KPI values, data-quality scores, and rule breaches are
   generated by an LLM completion, not computed. Identical input can produce different output
   across two runs.

Everything else — no persistence, no auth, no enforced tenant isolation, no tests — follows from
there being no backend at all.

The existing domain model (`frontend/types.ts`) is well designed and is kept as the API contract.
The existing UI components are kept and rewired to a real backend rather than rewritten from
scratch.

## Goal

Turn this into a sellable multi-tenant SaaS product: enterprise buyers upload warehouse data,
get deterministic KPIs and AI-generated narrative/insight text on top of those numbers, with real
auth, real tenant data isolation, and no secret ever reaching the browser.

## Scope decomposition (build order)

1. Data foundation + deterministic KPI engine (this spec)
2. Auth + tenant enforcement (this spec)
3. API + frontend integration (this spec)
4. AI agents layer (follow-on spec, after 1–3 land — see "AI agents layer" below for what and why)
5. Billing/subscription (follow-on spec, after v1 has users to bill)
6. Enterprise hardening pass — SSO/SAML, audit trail, load test, security review (follow-on spec)

This spec covers 1–3: everything required for a working, secure, deterministic, multi-tenant v1.
Billing and SSO are deliberately deferred — they're real work but they don't block having a
correct, sellable core product, and building them before the core is proven would be designing
for hypothetical scale. The AI agents layer (4) is deliberately sequenced *after* the core, not
before or alongside it: every agent below reasons over KPI/action data that only exists once
Phases 1–3 are built and running — an agent built first would have nothing real to query.

## Architecture

```
Browser (React/TS, existing UI kept)
   │  HTTPS + JWT
   ▼
FastAPI backend (Azure Container Apps)
   │
   ├── Postgres (Azure Database for PostgreSQL) — RLS enforced, single shared schema
   ├── Azure Blob Storage — raw uploaded files
   └── Gemini API (server-side only, key in Azure Key Vault) — narrative text ONLY,
       called after KPI numbers are already computed in Python
```

No client-side call ever reaches Gemini or Postgres directly. The browser only talks to the
FastAPI backend over authenticated HTTPS.

## Tenant isolation

Shared schema, every tenant-owned table carries `tenant_id`, enforced with Postgres Row-Level
Security policies set via `SET LOCAL app.tenant_id` on every request (session-scoped, not
trusted to app-layer `WHERE` clauses). This is the standard, auditable pattern for B2B SaaS at
this scale — defensible in an enterprise security questionnaire, and migrations stay a single
operation instead of an N-tenant fan-out. `tenants` itself has no `tenant_id` column (it's the
tenant registry, one row per tenant, not a table a tenant owns rows in) but is still
RLS-protected, scoped on its own `id` column instead — a tenant's session can only see its own
registry row, not enumerate every other tenant.

**Two DB roles, not one.** Postgres superusers bypass RLS unconditionally, regardless of
`FORCE ROW LEVEL SECURITY` — so the role the running application connects as must never be a
superuser, or the policy is decorative. `warehouse_migrator` (superuser-equivalent, can
`CREATE ROLE`/`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`) is used only by Alembic at deploy
time. `warehouse_runtime` (plain `LOGIN`, no `BYPASSRLS`, no superuser, granted only
table-level DML) is the role the FastAPI app actually connects as for every request — this is
the role RLS policies are written to restrict. It is additionally granted membership in the
narrow `app_bypass_auth` role (BYPASSRLS) used only for the cross-tenant login lookup, switched
to via `SET ROLE`/`RESET ROLE` for that single query.

## Data model (core tables)

- `tenants` — id, name, plan, created_at
- `users` — id, tenant_id, email, hashed_password, role, created_at
- `uploads` — id, tenant_id, file_name, file_type, blob_path, status, uploaded_by, created_at
- `ingestion_jobs` — id, upload_id, status (`PENDING`/`RUNNING`/`SUCCEEDED`/`FAILED`/`DEAD_LETTER`),
  attempt_count, last_error, created_at, updated_at — real retry/DLQ semantics, not a fire-and-
  forget background task. A failed job is visible and retryable, never silently dropped.
- `orders`, `picks`, `inventory` — canonical schema, same field names as the existing prompt's
  `ORDERS TABLE SCHEMA` / `PICKING TABLE SCHEMA` / `INVENTORY TABLE SCHEMA`
- `kpi_snapshots` — tenant_id, kpi_name, period_start, period_end, computed_value_json — stores
  history so trend/month-over-month comparisons are real lookups, not recomputation guesses
- `rule_configs` — tenant_id, rule_id, condition, threshold, priority — configurable per tenant,
  replacing the hardcoded thresholds in the current prompt
- `proposed_actions` — mirrors `ProposedAction` in `types.ts`, with real state-machine columns
  (status, approved_by, executed_at)

## Ingestion + KPI engine (the core correctness fix)

1. User uploads file → stored in Blob Storage, `uploads` row + `ingestion_jobs` row created
   (status `PENDING`).
2. Worker picks up job (Postgres `SELECT ... FOR UPDATE SKIP LOCKED` queue — no new infra
   dependency like Redis needed at this scale, and it's transactionally consistent with the rest
   of the data).
3. `pandas`/`openpyxl` parses the file. Column-mapper matches client headers to canonical schema
   (same mapping table as today's prompt, ported to a testable Python function, not a text
   completion).
4. Data-quality checks (completeness, type validation, cross-file consistency, duplicate
   detection) run as real pandas operations, producing the exact `DataValidationResult` shape
   already defined in `types.ts` — the frontend's rendering code does not need to change shape.
5. KPI engine computes cycle time / percentiles / trend deltas with `numpy`, evaluates
   `rule_configs` thresholds, and writes a `kpi_snapshots` row. Same output shape as
   `OrderCycleTimeKPI` / `RuleEngineResult` today.
6. Only after all numbers are computed, one Gemini call turns the finished KPI + rule result into
   the `executive_summary` narrative string. Gemini never sees raw data and never produces a
   number that ends up in a KPI field — a prompt-injected or hallucinated response can make the
   narrative text wrong, but it cannot corrupt a KPI value, because it's never on that code path.
7. Job status updates to `SUCCEEDED`. On any exception, `attempt_count` increments and the job is
   retried with backoff up to a cap, then moved to `DEAD_LETTER` with `last_error` populated and
   surfaced in the UI as a visible "upload failed" state — never a silent empty dashboard.

## Auth

`fastapi-users` (JWT-based), not hand-rolled — password hashing, verification, and session
handling are security-critical and a proven library is the safer engineering call over custom
code for a v1. Every user belongs to exactly one tenant. SSO/SAML is deferred to the hardening
phase; the auth model is built so an OIDC bridge can be added later without a data-model change.

## API + frontend integration

FastAPI exposes REST endpoints matching the existing domain shapes: `POST /uploads`,
`GET /uploads/{id}/status`, `GET /kpis`, `GET /kpis/{id}/history`, `GET /actions`,
`POST /actions/{id}/approve`, etc. The existing React components (`Dashboard`, KPI cards, action
lists) are kept; `services/geminiService.ts` is deleted from the frontend entirely and replaced
with an API client hitting the FastAPI backend. Auth adds a login screen in front of the existing
UI.

## AI agents layer (Phase 4 — follow-on spec, not built in this pass)

The original product's own pitch (`metadata.json`: "AI-driven corrective actions"; the GitHub
repo description: "helping them by providing AI assistant over their own data") already implies
more than narrative-text generation. Once the deterministic core (1–3) is live, three agentic
capabilities create real, defensible product value — "agentic" meaning multi-step and tool-using,
not a single completion call, and every one of them is a read-only reasoner over numbers Python
already computed, never a replacement for the computation itself:

1. **Conversational data assistant.** A tenant asks a question in plain language ("why did pick
   accuracy drop in Zone C last week?"); the agent calls read-only, tenant-scoped tool functions
   against the `kpi_snapshots` / `orders` / `picks` / `inventory` tables (through the same
   `tenant_scoped_session` every other code path uses — an agent gets no special DB access) and
   composes an answer from real query results. This is the single most differentiating feature
   versus a static BI dashboard, and it's what the product was originally pitched as.
2. **Action recommendation agent.** Today's plan has the rule engine deterministically decide
   *whether* a threshold breached and generate a static `action_template`. This agent adds
   judgment on top: given a triggered rule, it reasons over `historical_action_effectiveness`
   (already in `types.ts` — acceptance rate, execution rate, cumulative KPI improvement per past
   action) to rank *which* of the known interventions is most likely to work for this specific
   tenant's history, rather than always proposing the same generic template. The rule engine's
   trigger/severity/breach math is never touched by this agent — it only re-ranks and annotates
   an already-computed, already-triggered proposal. Every output remains a `PROPOSED` action
   requiring human approval before `ACCEPTED`/`EXECUTED` — the existing action-lifecycle state
   machine already enforces this gate, so the agent changes *which* action is suggested, never
   whether one gets executed automatically.
3. **Root-cause drill-down agent.** Given a KPI breach, an agent that iteratively queries the
   underlying order/pick/inventory rows (read-only, tenant-scoped, same tool-call pattern as #1)
   to isolate the actual driving segment (e.g. "cycle time degraded specifically for orders over
   50 units placed after 3pm in Zone B") rather than leaving the operator to dig through raw data
   themselves. Highest-effort of the three; sequence last within this phase.

All three are additive on top of the deterministic engine, never a dependency of it — the KPI
numbers, rule evaluations, and action proposals must work correctly with zero LLM involvement
before any of this phase starts, exactly as Phases 1–3 already specify.

## Testing

- Unit tests: column-mapper and KPI math against fixture Excel files (multiple malformed-input
  cases: missing required columns, duplicate rows, negative durations, future dates).
- Integration tests: real Postgres via TestContainers (not SQLite — RLS policies, `JSONB`
  columns, and timezone handling do not behave the same on SQLite and would silently mask bugs).
- Determinism test: run the same fixture file through the engine twice, assert byte-identical KPI
  output — this is the regression test for the exact defect this rebuild exists to fix.
- Failure-path tests: malformed file, DB unavailable during job processing, concurrent uploads to
  the same tenant.

## Out of scope for this spec (deferred, tracked above)

Billing/subscription, SSO/SAML, formal load testing, penetration test. Each gets its own spec
before being built.
